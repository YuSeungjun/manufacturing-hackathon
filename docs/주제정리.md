# 안전한 재가동 — 컨베이어 끼임 예방 인터록 + 반복 패턴 분석

## 한 문장

AI가 컨베이어 위험구역에 남아 있는 작업자를 감지해 위험한 재가동을 차단하고,
같은 상황이 몇 번 반복됐는지와 그때마다 라인이 몇 분 섰는지를 남기는
제철소 이송·회전설비 끼임 예방 시스템.

---

## 1. 문제

### 사고가 나는 순서

```
컨베이어에 원료 걸림  →  벨트 정지
  → 작업자가 이물을 빼러 측면으로 접근
  → 회전체(테일 풀리 · 구동 풀리)에 가까워짐
  → 다른 작업자가 내부 작업자를 확인하지 못함
  → 벨트 재가동
  → 끼임
```

### 이 순서의 진짜 문제

한 번이 아니라 **반복된다.** 같은 컨베이어에서 한 달에 마흔 번 걸리면 작업자는 마흔 번
회전체 옆으로 들어간다. 사고는 그중 한 번이고, 나머지 서른아홉 번은 아무 기록도 남지 않는다.

그래서 이 시스템은 사건을 두 번 쓴다.

| | 막는다 | 없앤다 |
|---|---|---|
| 보는 단위 | 사건 한 건 | 설비 한 대의 한 달 |
| 판정 | 잔류 × 설비 상태 → 인터록 | 정지 구간 × 위험접근 → 반복 패턴 |
| 결론 | "지금 재가동하면 안 된다" | "이 컨베이어를 고쳐야 한다" |
| 설득 대상 | 안전 | 생산 |

### 왜 지금인가

2024년 제조업 사고재해자의 **28.07%**, 사고사망자의 **29.41%** 가 끼임이었다.
그중 제조업 끼임 사망사고의 약 **54%** 가 정비·청소 같은 **비정형 작업** 중 발생했다.

정형 작업은 방호장치가 잡아 준다. 비정형 작업은 방호장치를 일부러 열고 들어가는 상황이라
남는 안전장치가 LOTO(시건)와 사람 사이의 확인뿐이다. 그 둘이 동시에 흔들릴 때 사고가 난다.

### 범위를 좁힌 이유

보호구 미착용이나 산업안전 전반을 다루지 않는다. **설비 이상 대응 중 발생하는 끼임 하나**에
집중한다. 넓게 벌리면 어느 것도 실제로 막지 못한다.

컨베이어를 앞에 세운 이유는 세 가지다.

1. **원인이 반복된다.** 걸림은 같은 지점에서 같은 이유로 다시 걸린다. 반복되는 것만 패턴으로
   찾아낼 수 있다.
2. **정지 신호가 실재한다.** 벨트 정지·모터 전류는 PLC 가 실제로 주는 값이다. 설비 상태
   타임라인이 요청 파라미터인 이 시스템의 구조가 컨베이어에서는 눈속임이 아니라 그대로 실물이다.
3. **경제 효과가 같은 사건에서 나온다.** 걸림은 안전 사건이면서 동시에 생산 중단 사건이다.
   한 번 세면 두 가지 이야기를 할 수 있다.

다만 판정 로직은 설비 종류를 가리지 않는다(`구역 × 잔류 × 설비상태`). 그래서 서비스 범위는
**제철소 이송·회전설비 끼임 예방**으로 두고 압연설비도 같은 화면에서 다룬다.

## 2. 해결

### 위험 판정 조건

```
작업자가 위험구역 내부에 잔류   AND   설비 가동 또는 재가동 명령   →   끼임 위험
```

끼임은 "사람이 들어간 사건"이 아니라 **사람이 안에 있는 채로 설비가 깨어난 사건**이다.
그래서 이 시스템의 중심은 점유 자체가 아니라 **설비 상태의 전이(edge)** 다.

### 결합 매트릭스

| 설비 상태 ＼ 구역 | 비어있음 | 진입 | 잔류 |
|---|---|---|---|
| 시건 완료(LOTO) | 정상 | 기록 | 기록 |
| 정지(시건 없음) | 정상 | 주의 | 경고 |
| 재가동 요청 | 정상 | **위험** | **위험** |
| 가동 중 | 정상 | **위험** | **위험** |

시건이 걸린 정상 작업은 경보가 아니라 기록이다. 여기서 경보를 울리면 현장은 하루 만에
시스템을 끈다.

### 전체 흐름

```
CCTV 영상
  → 작업자 탐지·추적
  → 위험구역 진입/잔류 판단
  → 설비 상태와 결합
  → 위험 판정
  → 재가동 차단 (인터록)
  → 위험 순간 캡처 + 전후 클립 저장
  → 관리자 즉시 통보
  → 현장 확인
  → 현장 조치·개인 시건 해제 → 재요청 → 재가동
```

### 정지 에피소드 — 같은 사건을 두 번째로 쓰는 방법

AI 는 "제품이 걸렸다" 를 보지 못한다. 걸림 클래스를 학습한 모델이 없고, 있어도 라인마다
걸리는 모양이 다르다. 관측 가능한 것은 두 개뿐이다.

```
① 설비가 멈춰 있다        ← PLC / LOTO / 화면 입력이 주는 상태 타임라인
② 사람이 위험구역에 있다   ← 영상 분석이 주는 위험 사건
```

`StoppageEpisode` 는 ①에서 `정지 → 재가동` 구간을 자르고 ②를 그 구간에 붙인 것이다.
그래서 이 표가 말하는 문장은 "걸림을 감지했다" 가 아니라 **"정지 구간 안에서 위험구역
접근이 있었다"** 다. 후자는 실제로 잰 것이고 전자는 아니다.

| 필드 | 뜻 |
|---|---|
| `cause` | `JAM` / `MAINTENANCE` / `OTHER` — 위험접근이 동반된 정지만 걸림으로 추정하고, 관리자가 되돌릴 수 있다 |
| `recoverySec` | 정지 → 재가동. 재가동 전이면 0 이고 평균에서 빠진다 |
| `riskApproach` | 이 구간에 위험 사건이 있었는가. **반복 패턴의 대상은 "정지"가 아니라 "정지 + 위험접근"** 이다 |
| `source` | `AI`(영상에서 파생) / `PLC` / `MANUAL` |

### 입력은 CCTV 가 찍어 둔 장면이다

안전관리자는 자기 컴퓨터에서 사진을 올리는 사람이 아니다. **카메라가 이미 찍어 둔 장면
중에서 볼 것을 고르는** 사람이다. 그래서 분석 화면에 파일 선택 대화상자가 없다.

```
CCTV — 위험구역 접근 감지 → 스냅샷 자동 저장
                                    ↓
                    스냅샷 수신함 — 카메라 · 촬영 시각 · 촬영 이유
                                    ↓
                  안전관리자가 볼 장면을 골라서 → AI 분석 → 위험 사건
```

수신 경로는 `POST /api/snapshots` 다. 사람 세션이 아니라 **장치 토큰**으로 인증한다 —
카메라는 로그인하지 않는다. 화면의 "수신 시뮬레이션" 은 데모 이미지를 같은 수신함에
넣기 위한 우회로이고, 접혀 있고 그렇게 적혀 있다.

**이 구조의 실익은 시각이다.** 분석할 때 사람이 촬영 시각을 입력하면 오타 하나가
잔류시간을 거짓으로 만든다. 찍힌 순간에 한 번 기록되면 그 뒤로는 데이터고, 분석 화면에서
사람이 넣는 값은 하나도 없다 — 설비 상태만 데모에서 받고 그것도 실운영은 PLC 가 준다.

`CameraSnapshot` 에는 `trigger`(왜 찍혔나)도 함께 남는다. `ZONE_APPROACH` 로 찍힌 장면이
수신함에 쌓이는 것 자체가 "위험구역 접근이 반복된다" 는 1차 증거다.

### 수신 시점 1차 탐지

카메라가 "접근했다" 고 말하면 **그 근거가 함께 있어야 한다.** 수신할 때 프레임 한 장을
판정해 사람 박스를 붙여 두고, 수신함 썸네일이 그걸 그린다.

| | 표시 |
|---|---|
| 구역 안 작업자 | 진한 실선 박스 + `IN ZONE 0.74` |
| 구역 밖 사람 | 얇고 흐린 박스, 라벨 없음 |
| 점유된 구역 | 진한 폴리곤 |
| 빈 구역 | 얇은 점선 |

**박스는 빨개지지 않는다.** 기계는 사람이 어디 있는지 탐지할 뿐 위반을 정하지 않고, 빨강은
사람이 확정한 뒤에만 쓴다. 배지도 같다 — "구역 안 1명" 은 강조(act)까지고 경고(deny)가 아니다.

두 가지를 구분해서 남긴다.

- **1차 탐지는 판정이 아니다.** 잔류도, 설비 상태 결합도, 사건 생성도 하지 않는다.
  그건 여러 장을 묶는 시퀀스 분석 몫이다. 여기서 하는 건 "이 한 장에 사람이 어디 있었나" 뿐이다.
- **탐지 실패는 수신 실패가 아니다.** AI 서비스가 재시작 중이라고 카메라가 보낸 장면을
  잃으면 정작 필요한 순간의 근거가 사라진다. 그래서 실패는 빈 결과가 되고 `detectedAt` 이
  비어 남는다 — "탐지하지 않았다" 와 "탐지했는데 사람이 없었다" 는 다른 사실이고,
  화면도 "탐지 안 됨" 과 "사람 없음" 으로 다르게 적는다.

기본 입력은 이렇게 받은 **정지 이미지 여러 장**이다. 영상 경로도 남겨 뒀지만 부차적이다.

```
정상 운전  →  벨트 정지  →  작업자 접근  →  위험구역 진입  →  재가동 요청
 14:32:07     14:32:37      14:33:07        14:33:37         14:34:07
  (1장)        (2장)         (3장)           (4장)            (5장)
```

한 장으로는 "사람이 있다" 까지다. 여러 장이라야 "설비 이상에 대응하려고 위험구역으로
접근하는 행동" 이 된다. 그래서 한 장씩 판정하지 않고 시퀀스로 넣는다. 결과 계약
(`AnalyzeResult`)이 영상과 같아서 위험 사건·정지 에피소드·패턴 집계가 그대로 얹힌다.

영상 경로와 세 가지가 다르고, 셋 다 정직해야 성립한다.

| | 영상 | 캡처 이미지 |
|---|---|---|
| 샘플링 | 6fps | 업로드한 장수 그대로 |
| 작업자 추적 | ByteTrack | **안 한다.** 프레임이 초 단위로 떨어지면 모션 예측이 성립하지 않는다. 이어붙인 척하면 잔류시간이 조용히 거짓이 된다 |
| 진입 판정 | 2프레임 투표(0.33초) | **한 장이 곧 관측.** 6fps 기준 히스테리시스를 30초 간격에 그대로 걸면 "진입 확정까지 60초" 가 된다 |
| 잔류시간 | 초 단위 | **프레임 간격 단위.** 30초 간격이면 "6.4초 잔류" 는 만들 수 없다 |

추적을 버려도 판정이 흔들리지 않는 이유는 처음부터 **CRITICAL 이 track id 가 아니라 구역
인원수만 보게** 짜였기 때문이다. 영상용으로 만든 그 설계가 이미지 경로에서 값을 한다.

마지막 줄의 해상도 한계는 `warnings` 로 화면까지 나간다. 지우면 안 되는 문장이다.

### 관측되지 않은 공백은 존재의 증거가 아니다

이건 만들면서 실제로 깨진 지점이다. 6.7시간 떨어진 두 장을 같이 골랐더니 **"잔류
24,261초"** 가 나왔다. 계산은 맞았고 주장이 틀렸다 — 그 사이를 우리는 보지 않았다.

그래서 고른 두 장 사이가 `min(전형 간격 × 3, 180초)` 를 넘으면 앞뒤를 이어 붙이지 않고
빈 관측을 흘려 사건을 닫는다. 같은 여섯 장이 이제 이렇게 나온다.

| 선택 | 결과 |
|---|---|
| 6.7시간 공백 포함 6장 | 사건 **2건** — 잔류 0초 + 잔류 120초. 공백을 건너뛰지 않는다 |
| 연속 5장 (30초 간격) | 사건 1건 — 잔류 **120초** (30초 × 4구간) |

절대 상한이 있는 이유는 10분 간격 스틸로 "잔류 30분" 을 만들지 않기 위해서다. 그 정도로
드문 관측으로 연속 체류를 주장할 수는 없고, 그러면 잔류 판정이 아예 안 나오는 게 맞다.

이미지에 박힌 타임스탬프를 OCR 하지 않는다 — 번인 문자열은 카메라마다 위치·서체가 다르고
한 글자를 잘못 읽으면 잔류시간이 거짓이 된다. 시각은 찍은 장치가 준다.

### 안전대 — 어디까지 보고 어디서 멈추는가

경계선을 감으로 긋지 않고 데모 화각(`samples/` 의 CAM 05)에서 픽셀을 재서 그었다.

| | 실측 | 판정 |
|---|---|---|
| 척도 | 안전모 폭 28cm ≈ 47px → **1.7 px/cm** | — |
| 하네스 웨빙 | 45mm ≈ **7~8px** | 보인다. 어깨 스트랩·허리 버클·D링이 육안으로 확인된다 |
| 카라비너 | 10~24cm ≈ **17~41px** | 크기는 되지만 몸·구조물에 가린다 |
| 랜야드 | 2m ≈ **340px** | 카라비너보다 열 배 크다 |

**착용까지는 본다.** 다만 전체 프레임에서 7px 스트랩을 찾지 않는다. 사람 탐지가 이미
conf 0.9 로 되므로 `사람 bbox → 상체 crop(190×170px) → 착용/미착용 분류` 로 쪼갠다.
그러면 스트랩이 입력 폭의 4% 가 되어 CNN 이 볼 수 있는 크기가 된다. 공개 데이터가
100장 단위인 상황에서 탐지기를 새로 학습하는 것보다 훨씬 현실적이다.

**체결은 보지 않는다.** 두 가지 이유다.

1. 훅이 안 보이는 것이 "미체결" 인지 "가려짐" 인지 구분할 방법이 없다. 미탐과 무탐이
   같은 그림이라 신뢰구간을 잡을 수 없다.
2. 체결의 옳고 그름은 물체가 아니라 **관계** 다. 정격 앵커에 걸었나, 난간에 걸었나
   (난간은 앵커로 부적합), 자기 하네스 D링에 걸었나(가짜 체결). 픽셀에 그 정보가 없다.
   산업계도 이건 홀센서·스트레인게이지로 푼다 — 비전으로 안 되니까 특허가 그렇게 났다.

### 버튼을 두 개로 가른 이유

수신함에서 장면을 고르면 버튼이 두 개 뜬다.

| 버튼 | 질문 | 공급자 |
|---|---|---|
| 위험구역 분석 | 진입·잔류했나 | 우리 로직 — 사람 탐지 + 폴리곤 + 설비 상태 결합 |
| 안전대 착용 판정 | 하네스를 입었나 | Roboflow 호스팅 추론 — **남의 학습 결과** |

한 버튼에 묶으면 남의 추론 서비스가 죽는 날 우리 판정까지 같이 의심받는다. 그래서 상태도
따로 두고, 실패 메시지도 따로 뜬다. `GET /health` 의 `harness.provider` 가 어디서
판정하는지 밝히고(`roboflow` / `local` / `none`), 실패 이유는 `harness.error` 로 나간다.

`ai/harness.py` 는 공급자를 셋 중에서 고른다 — Roboflow 키+모델이 있으면 원격, 없으면
로컬 가중치, 둘 다 없으면 판정하지 않는다. 모델 id 는 환경변수라 갈아타는 데 코드 수정이
없다.

### 실측: Roboflow 는 지금 못 쓴다

키(`api.roboflow.com`)는 유효하고 데이터셋 다운로드도 된다. 그런데 **추론 엔드포인트가
전부 HTTP 500** 이다 — 우리 요청 형식 문제가 아니라, Roboflow **자기 데모 모델(`coco/9`,
`rock-paper-scissors-sxsw/11`)도 500** 이다. 호스트(`detect` / `serverless`)와 본문 형식
(multipart / base64 / JSON)을 다 바꿔 봐도 같다.

| | 결과 |
|---|---|
| 키 인증 (`api.roboflow.com`) | 정상 |
| 데이터셋 내보내기·다운로드 | 정상 (`harness-uvoia` v3, 라벨 383개) |
| 호스팅 추론 (모든 모델·모든 형식) | **HTTP 500** |
| 상체 crop 크기 | 147 / 153px — 최소치(48px)의 3배. **이미지 탓이 아니다** |

그리고 Universe 에서 학습본이 있는 하네스 모델은 `harness-uvoia/1`(mAP 54, 97장) 하나뿐인데,
**두 클래스를 눈으로 확인해 보니 `0`도 `1`도 둘 다 하네스였다** — 착용/미착용 구분이 아니다.
클래스 이름이 `'0'`/`'1'` 이라 매핑도 추측이 된다. 클래스가 좋은
`harness_detection-coo5d`(1431장, `full-body-harness`·`Lifeline`·`belt_hook`)는 학습된 버전이
0개라 호스팅 추론이 아예 없다.

### 그래서 CLIP 제로샷으로 갔다

인터넷이 되는 건 처음부터였고, 막힌 건 우리 연결이 아니라 그쪽 500 이었다. 대신 다른 길이
열렸다 — **학습도 라벨도 없이** 상체 crop 을 두 문장과 비교하는 것이다.

먼저 안 되는 것을 확인했다. YOLO-World 로 "safety harness" 를 **물체로** 찾으면 0.02 다.
같은 모델이 "person" 은 0.91, "hard hat" 은 0.56 을 낸다 — 흔한 개념은 알지만 하네스는
이 해상도에서 못 찾는다.

**탐지 대신 분류로 바꾸면 된다.** 사람 위치는 우리 탐지기가 이미 잡아 주므로 남는 문제는
crop 한 장의 2지선다이고, 그건 CLIP 이 한다.

| 프롬프트 | 무릎 꿇은 작업자(착용) | 걸어오는 작업자(미착용) |
|---|---|---|
| A "wearing a safety harness" | ✗ 0.417 | ✓ 0.482 |
| **B "black harness straps across the back"** | **✓ 0.980** | **✓ 0.333** |
| C "fall-protection full body harness" | ✓ 0.937 | ✗ 0.779 |

**프롬프트가 성능을 지배한다.** 같은 두 장에서 문장만 바꿔 A 는 하나, C 는 하나를 틀렸다.
그래서 프롬프트를 코드에 박지 않고 환경변수로 뺐고, 어떤 문장을 썼는지 `/health` 에 싣는다.

그리고 **표본이 2명이다.** 2장에서 맞는 프롬프트를 고른 건 테스트셋에 과적합한 것과 같아서,
이 숫자를 성능이라고 말하면 안 된다. 판정이 경계에 걸려 있다는 증거도 있다 — 같은 사진을
JPEG 로 재인코딩했더니 착용확률이 0.551 에서 0.611 로 움직여 UNKNOWN 과 NOT_WORN 사이를
넘나들었다.

그래서 **마진을 둔다.** 두 문장의 확률 차이가 0.20 보다 작으면 UNKNOWN 이다. 0.51 대 0.49 를
"착용" 이라고 부르는 건 판정이 아니라 동전 던지기다.

공급자는 셋 중에 고른다(`HARNESS_PROVIDER`): `roboflow`(살아나면) · `clip`(지금 기본) ·
`local`(직접 학습한 가중치). 환경변수 하나라 갈아타는 데 코드 수정이 없다.

Roboflow 버튼도 지우지 않았다. 배선은 그대로 있고, 그쪽이 살아나면 `HARNESS_PROVIDER=roboflow`
한 줄로 돌아간다.

### 화면에는 두 줄이 나란히 뜬다

 AI 추정 한 줄("하네스 미착용이 의심됩니다 71%
· 착용까지만 본 값이고 체결은 아닙니다")과, 사람이 누르는 체결 확인 버튼.
`DangerZone.requiresHarness` 로 표시한 구역만 뒤쪽 버튼이 열린다.

이 선언은 문서가 아니라 계약이다 — `GET /health` 의 `harness.judgesAttachment: false`.

**부수 확인** — 저장 캡처는 bbox 상단 28%(머리)를 블러 처리하는데, 하네스는 그 아래
몸통에 있어 블러가 근거를 지우지 않는다. 개인정보 처리와 착용 판정이 충돌하지 않는다.

## 3. 차별점

포스코와 해외 제철소에도 위험구역 진입을 감지해 알람을 보내는 AI CCTV 가 실제로 쓰이고 있다.
따라서 "진입 감지 후 알림"만으로는 차별성이 없다.

| | 기존 AI CCTV | 이 시스템 |
|---|---|---|
| AI 의 역할 | 알림 | **재가동 차단 + 반복 패턴 발견** |
| 판정 기준 | 구역 진입 | 잔류 × **설비 상태 결합** |
| 사고 직전 | 사람이 알람을 봐야 함 | 설비가 안 돌아감 |
| 해제 | 해당 없음 | **현장 확인한 사람만** |
| 오탐 처리 | 알람 무시 | 오탐 판정해도 인터록은 안 풀림 |
| 근거 | 로그 | 캡처 + 전후 클립 + 폴리곤 스냅샷 |
| 남는 것 | 탐지 로그 | **설비별 걸림 횟수 · 복구시간 · 누적 중단시간** |
| 보고 대상 | 안전관리자 | 안전관리자 **+ 생산·경영** |

### 설계 원칙 네 가지

**① 차단은 기계가, 해제는 사람만.**
AI 는 안전한 방향으로만 자동 개입한다. 막는 것은 자동, 푸는 것은 수동.

**② 판정과 해제를 분리한다.**
위험 사건을 오탐으로 판정해도 인터록은 자동으로 풀리지 않는다. 판정은 사후 정확도 기록이고
해제는 현장을 확인하고 내리는 조치다. 하나로 묶으면 "오탐 버튼이 곧 해제 버튼"이 된다.

**③ 근거는 두 개여야 한다.**
AI 판정 하나만으로 차단하면 오탐 하나에 라인이 선다. 그래서 개인 시건(LOTO)을 두 번째
근거로 함께 본다. 시건은 오탐이 없다.

**④ 탐지가 멈춰도 안전 쪽으로 실패한다.**
인터록 판정은 DB 만 본다. AI 서비스가 죽었다고 재가동이 자동 허용되면 안 된다.

**⑤ 못 보는 것은 못 본다고 적는다.**
제품 걸림도, 안전대 체결도 AI 가 판정하지 않는다. 관측 가능한 신호의 조합으로 정의하거나
사람이 채우는 칸을 열어 둔다. 금액도 마찬가지다 — 분당 손실단가는 관리자 입력값이고
비어 있으면 금액 칸 자체가 사라진다.

### 기존 안전장치와의 관계

기존 LOTO 와 방호장치를 **대체하지 않는다.** 안전절차 누락과 작업자 간 의사소통 오류를
보완하는 **AI 이중 안전장치**로 정의한다.

## 4. 역할

| 역할 | 하는 일 |
|---|---|
| 안전관리자 | 작업조·투입자 설정, 영상 분석, 위험 사건 판단과 현장 조치 완료 기록 |
| 설비 운전 담당자 | 재가동 요청 — 작업자가 남아 있으면 차단당한다 |
| 정비 작업자 | 개인 시건 시건/해제. 보호 대상이지 감시 대상이 아니다 |

**개인 작업자를 점수화하지 않는다.** 현황판의 조 점수는 안전관리자가 확정한 사건만 작업조의
개선 지표로 반영하며, 개인 식별이나 개인별 감점에는 사용하지 않는다. 노출시간과 차단 횟수도
함께 표시해 점수 하나만으로 현장을 판단하지 않도록 한다.

## 5. AI가 하는 일

**한다**

- 작업자 탐지 (COCO `person` 한 클래스)
- 작업자 추적 (ByteTrack, 익명 track id)
- 위험구역 폴리곤 진입 판단
- 잔류 시간 누적
- 설비 상태와 결합한 위험 판정
- 위험 순간 자동 캡처 + 전후 클립
- 정지 구간과 위험 사건을 묶은 설비별 반복 패턴 집계
- 안전대 **착용** 추정 (상체 crop 분류, 별도 모델이 있을 때만)

**하지 않는다**

- 얼굴 인식 · 개인 식별
- 안전모·조끼 등 일반 보호구 착용 판정
- 작업자 감시 · 근태 추적
- **제품 걸림 판정** — 관측하는 건 `벨트 정지` × `위험구역 접근` 두 개다
- **안전대 체결 판정** — 착용까지만 본다. 훅은 화각에 안 잡히고, 무엇에 걸었는지는 픽셀에 없다
- **이미지 시퀀스에서의 작업자 추적** — 프레임이 희소하면 성립하지 않는다

`track id` 는 한 영상 안에서만 쓰이고 분석이 끝나면 사라진다. 저장되는 캡처는 bbox 상단
28%(머리)를 블러 처리한다. 이 선언은 `GET /health` 응답의 `identifiesIndividuals: false`,
`faceBlur: true` 로 코드에 박혀 있다 — 문서가 아니라 계약이다.

### 기술 판단

**왜 파인튜닝하지 않는가**

1. **못 한다.** AI-Hub 원천 영상이 100GB 분할압축이라 부분 다운로드가 불가능하다.
   라벨 JSON 만으로는 검출기를 학습할 수 없다 — 픽셀이 필요하다.
2. **필요 없다.** COCO `person` 은 26만 인스턴스로 최다 클래스다. "여기 사람이 서 있는가"는
   nano 모델도 천장 근처다.
3. **실패 모드가 다르다.** 이 문제의 오차는 분류 오류가 아니라 기하 문제다 — 롤 스탠드 뒤
   가림, 원거리 20px 작업자, 반사. 파인튜닝이 아니라 카메라 배치와 임계값으로 푼다.
4. **가치가 로직층에 있다.** 구역 × 잔류 × 설비상태 결합은 학습 데이터가 0바이트도 필요 없다.
5. **역행 경로가 있다.** 원천이 들어오면 `PERSON_MODEL` 환경변수만 바꾸면 되고 API 계약은
   그대로다.

**어디에 공을 들였는가**

- **발끝 5점 점유 판정** — 고정 CCTV 는 바닥면을 사영한 영상이라 "구역 안"은 접지점이
  폴리곤 안이라는 뜻이다. 중심점을 쓰면 카메라에 가까운 작업자는 오탐, 경계 밖에서 몸을
  기울여 넣으면 미탐이 난다. 하단 변 5점을 뽑아 0/1 이 아닌 연속 점유 점수를 만든다.
- **비대칭 히스테리시스** — 진입은 0.33초, 이탈은 0.67초. 한두 프레임 미탐으로 잔류
  타이머가 리셋되면 안 된다. 진입 시각 소급 보정과 이탈 되감기가 없으면 잔류시간이 매
  진입마다 체계적으로 어긋난다.
- **이벤트 에스컬레이션** — "진입 → 잔류 → 재가동"을 새 이벤트 세 건이 아니라 한 건의
  서사로 남긴다.
- **id 비의존 위험 판정** — CRITICAL 은 구역 점유 인원수만 본다. 프레임 샘플링으로 track id
  가 끊겨도 "재가동 시점에 안에 사람이 있었다"는 흔들리지 않는다.

## 6. 데이터

AI-Hub [「스마트 제조 시설 안전 감시를 위한 데이터」](https://www.aihub.or.kr/aihubdata/data/view.do?dataSetSn=71679)
— 제조시설 CCTV 20,000개, 끼임(`jam`) 영상 2,000개, 추출 이미지 40,000장, 바운딩박스·세그멘테이션 라벨.

**원천 영상은 쓰지 않는다.** Training 원천이 `TS.z01~z13 + TS.zip` 100GB 분할압축(약 1.3TB)
이라 조각 하나만 받아서는 압축을 풀 수 없다. 라벨은 `TL.zip` 602MB + `VL.zip` 74MB 로
현실적이다.

라벨은 학습이 아니라 **로직층 평가**에 쓴다 — 검출기 출력 자리에 정답 bbox 를 그대로 넣어
상태머신만 채점한다. 검출기 mAP 는 픽셀 없이 못 재지만, 이 시스템에서 실제로 중요한 건
검출기가 아니라 결합 로직이고 그건 라벨만으로 완전히 평가된다.

### 라벨을 세어 본 결과

`VL.zip`(Validation) 2,000 클립의 메타를 전부 읽어 보면 이렇다.

| 사건 | 클립 | 주요 설비 |
|---|---|---|
| `jam` (끼임) | 200 | injection-machine 107 · molding-machine 44 · machine-tool 17 |
| `fall-off` (추락) | 200 | injection-machine 124 · molding-machine 38 |
| `hit` · `bump` · `fall-down` | 450 | overhead-crane 71 · movable-stand 52 |

설비 이름으로 세면 `conveyor-belt` 는 **17 클립뿐이고 전부 `bump`(부딪힘)** 다. 컨베이어에서
난 `jam` 은 **0건**이다.

그래서 이렇게 정리한다.

- **화면과 데모의 주인공은 컨베이어**로 둔다. 문제 서사(걸림 → 접근 → 중단)가 가장 선명하고
  PLC 신호가 실재하는 설비다.
- **서비스 범위는 "제철소 내 이송·회전설비 끼임 예방"** 으로 넓게 적는다. 판정 로직이 설비
  종류를 가리지 않으므로 과장이 아니다.
- **공개 데이터 근거로는 `jam` 200 클립 전체**를 쓴다. 컨베이어 단독으로 못 박으면 근거가
  17 클립으로 줄어든다.
- 원천 영상이 없으므로 **데모 프레임은 자체 제작**한다 (`samples/`).

이 숫자를 문서에 적어 두는 이유는, 심사에서 "컨베이어 데이터가 얼마나 있나" 를 물었을 때
세어 본 사람과 안 세어 본 사람의 답이 다르기 때문이다.

## 7. 증명 지표

도입 효과를 사고 건수로 주장하지 않는다. 사고는 원래 드물어서 "줄었다"를 증명할 수 없다.
실제로 잰 시간과 횟수로만 말한다.

| 지표 | 계산 |
|---|---|
| 위험 감지 소요시간 | 구역 진입 → AI 위험 판정. 평균과 95분위 |
| 관리자 조치 소요시간 | 통보 → 인지 / 판단 / 현장 조치 완료 세 구간 |
| 위험구역 노출시간 | 구역별 + 현장 시간대(24시간) 히트맵 |
| 차단한 위험 재가동 | 차단 요청 수, 그중 사람이 위험으로 확정한 수 |
| CCTV 확인 업무시간 | 전체 영상 길이 대비 실제로 본 구간의 비율 |
| 오탐 / 미탐율 | 미판단(대기·보류)은 분모에서 빼고 따로 표기 |

**미탐율을 세는 방법** — 관리자가 "AI 가 놓쳤다"고 직접 등록하는 경로를 만들어 두었다.
이게 없으면 "오탐은 세는데 미탐은 안 센다"는 흔한 자기기만에 빠진다.

**시간당 오경보(FAR)** — 경보 시스템에서 운영자가 실제로 신경 쓰는 값이고, 라벨이 전혀
없어도 잴 수 있다. 정상 조업 영상에서 울린 모든 경보가 오경보다.

### 사업주에게 보여주는 네 개

안전 지표는 안전관리자를 설득하고, 이쪽은 결재권자를 설득한다. 같은 사건에서 나온다.

| 지표 | 계산 | 주의 |
|---|---|---|
| 걸림 대응 정지 횟수 | 설비별 `cause = JAM` 에피소드 수 | 계획 정비를 걸림으로 세면 통계가 거짓이 된다 |
| 위험구역 접근 동반 | 그중 `riskApproach = true` | 이게 실제 위험 신호다. 정지 자체는 아니다 |
| 평균 복구시간 | 정지 → 재가동 | 재가동 전인 건은 평균에서 제외. 0 을 섞으면 짧아 보인다 |
| 누적 생산중단시간 | 걸림 정지 구간의 합 | **계획 정비는 뺀다.** 넣으면 "정비하면 손해" 가 된다 |

금액은 `누적 중단시간 × 분당 손실단가` 하나뿐이고, 단가는 관리자 입력값이다. 비워 두면
금액 칸이 사라지고 횟수와 시간만 남는다 — 그게 기본값이다.

### 패턴 경고를 켜는 기준

임계값은 `src/lib/patterns.ts` 한 곳에 모아 두었다. "왜 3번이냐" 를 물으면 열어서 보여준다.

| 경고 | 조건 | 이유 |
|---|---|---|
| 반복 접근 | 한 설비 위험접근 ≥ 3건 | 2회는 우연일 수 있다 |
| 집중 | 전체 위험접근 ≥ 5건 **이고** 한 설비가 50% 이상 | 3건 중 2건으로 "67% 집중" 이라 말하면 통계가 아니다 |
| 느린 복구 | 걸림 ≥ 3건 이고 평균 복구가 전체 평균의 1.5배 이상 | 복구가 길수록 위험구역 체류도 길어진다 |

## 8. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 오탐으로 라인이 선다 | LOTO 시건을 두 번째 근거로 함께 본다. 히스테리시스로 경계 어른거림을 흡수한다. 테이크 C(스쳐 지나감)로 오탐 없음을 실측한다 |
| 미탐으로 사고가 난다 | 기존 LOTO·방호장치를 대체하지 않는 **이중** 안전장치로 정의한다. 관리자 직접 등록 경로로 미탐을 계속 센다 |
| 개인정보 | 얼굴 인식 미사용, 익명 track id, 캡처 머리 블러. `/health` 응답에 선언을 박아 계약화 |
| CPU 로 실시간이 되나 | 데모는 업로드 영상 배치 분석 + 타임라인 재생. 상용은 RTSP 게이트웨이. 화면 각주와 README 에 명시 |
| AI 서비스 장애 | 인터록 판정은 DB 만 본다. 탐지가 멈춰도 재가동은 자동 허용되지 않는다 |
| 카메라 화각 변경 | 폴리곤을 판정 시점 스냅샷으로 사건에 함께 저장한다. 구역을 고쳐도 과거 근거가 흔들리지 않는다 |

## 9. 확장

- PLC / MES 연동 — 현재 요청 파라미터인 설비 상태 타임라인을 실제 신호로 교체한다.
  **API 계약은 바뀌지 않는다.** 정지 에피소드도 같은 신호로 자동 생성된다
  (`StoppageEpisode.source = PLC`).
- 걸림 원인 분류 — 지금은 위험접근 동반 여부로 추정하고 사람이 고친다. 정지 직전 벨트 하중·
  전류 패턴이 들어오면 원인을 나눌 수 있다.
- 반복 패턴 → 작업 표준 개선 제안 — "이 설비는 걸림 후 접근이 84% 다" 에서 "이 설비에
  청소구를 달면 접근이 사라진다" 로 넘어가는 자리
- RTSP 게이트웨이로 실시간 스트림 연결
- 원천 데이터 확보 시 `yolo train` 으로 도메인 파인튜닝 (`PERSON_MODEL` 교체만)
- 중대재해처벌법 증빙 — `EquipmentStateLog` 가 "누가 언제 무엇을 근거로 풀었는가"를 남긴다

## 10. 구현 현황

**된 것**

- 위험구역 폴리곤 캔버스 편집기 (정규화 좌표, 키보드 폴백)
- 영상 업로드(Blob 직업로드) → 잡+폴링 분석 → 타임라인 동기 재생
- 발끝 5점 점유 · 비대칭 히스테리시스 · id 스티칭 · 이벤트 에스컬레이션
- 재가동 요청 → 차단 → 사건 판단·현장 조치 → 시건 해제 → 재요청 → 재가동 전 구간
- 6개 지표 대시보드, 구역별·시간대별 히트맵
- 정지 에피소드 자동 파생 (분석 결과의 설비 상태 타임라인 → 정지 구간 → 위험 사건 연결)
- 반복 패턴 화면 — 설비별 걸림·위험접근·복구시간·누적 중단시간·손실 환산, 패턴 경고 3종
- **스냅샷 수신함** — `POST /api/snapshots`(장치 토큰) 로 받은 장면을 골라 분석. 촬영 시각이 붙어 있어 사람이 넣는 값이 없다
- **정지 이미지 시퀀스 분석** — 장별 점유 → 잔류 누적(공백은 끊음) → 같은 위험 사건·에피소드
- 안전대 체결 확인 (구역 지정 → 사건에 사람이 채우는 칸)
- 안전대 착용 추정의 계약·배선 (`harness` 필드, `/health` 선언). 모델이 없으면 `null` 을 낸다
- 안전대 분류기 학습 스크립트 (`ai/train_harness.py` — 탐지 라벨 → 상체 crop → 분류 학습)
- 순수 로직 단위 테스트 32개, 데모 클립 채점기

**안 된 것**

- **안전대 분류기 가중치** — 배선과 학습 스크립트는 끝났고 데이터가 없다. Roboflow Universe
  가 API 키를 요구하고(Cloudflare 가 스크래핑 차단), HuggingFace 에는 하네스 클래스를 가진
  데이터셋이 없다. 확인한 것: `ggilabert/PPE_Detection` 은 6클래스에 하네스 없음,
  `Chapian/PPE_detection` 은 라벨이 게임 건물로 잘못 올라가 있음,
  `thalostech2025/thalos-scaffold-harness-safety-v1` 은 카드에 하네스라 적혀 있지만 실제
  클래스가 도로 위험물(pothole·manhole·bollard)이다 — 모델 카드를 믿지 말고 클래스를 직접 열 것
- 실시간 RTSP 스트림
- AI-Hub 라벨 리플레이 평가 (데이터 승인 대기)
- 다중 카메라 화각 융합
