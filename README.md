# 안전한 재가동

> AI가 컨베이어 위험구역에 남아 있는 작업자를 감지해 위험한 재가동을 **차단**하고,
> 같은 상황이 몇 번 반복됐는지와 그때마다 라인이 몇 분 섰는지를 남기는
> 제철소 이송·회전설비 끼임 예방 시스템.

두 축으로 움직인다.

| | 막는다 | 없앤다 |
|---|---|---|
| 대상 | 지금 이 순간의 사고 | 반복되는 위험 작업 자체 |
| 수단 | 재가동 인터록 | 정지 에피소드 집계 |
| 화면 | `/manager/events` `/operator` | `/manager/patterns` |
| 설득 대상 | 안전 | 생산 |

## 왜

컨베이어에 원료가 걸리면 벨트가 선다. 그러면 작업자가 이물을 빼러 측면으로 접근하고,
회전체인 테일 풀리·구동 풀리 근처까지 들어간다. 이때 다른 사람이 내부 작업자를 확인하지
못하고 벨트를 재가동하면 치명적인 끼임 사고가 된다.

문제는 이 순서가 **한 번이 아니라 반복된다**는 점이다. 같은 컨베이어에서 한 달에 마흔 번
걸리면, 작업자는 마흔 번 회전체 옆으로 들어간다. 사고는 그중 한 번이다.

2024년 제조업 사고재해자의 **28.07%**, 사고사망자의 **29.41%** 가 끼임이었고, 제조업 끼임
사망사고의 약 **54%** 가 정비·청소 같은 비정형 작업 중 발생했다.
([안전보건공단 산업재해 자료](https://www.kosha.or.kr/ebook/fcatalog/access/ecatalogt.jsp?Dir=636&callmode=normal&catimage=&eclang=ko&start=52&um=s),
[끼임 사망사고 분석](https://www.kosha.or.kr/ebook/fcatalog/access/ecatalogt.jsp?Dir=493&callmode=normal&catimage=&eclang=ko&start=38&um=s))

## 무엇이 다른가

포스코를 포함해 위험구역 진입을 감지하고 알람을 보내는 AI CCTV 는 이미 현장에 있다.
"진입 감지 후 알림"만으로는 차별성이 없다.

**이 시스템은 알림에서 멈추지 않는다.**

```
작업자가 위험구역 내부에 잔류  ─┐
                              ├─→  끼임 위험  →  재가동 차단  →  현장 조치·시건 해제  →  재요청
설비 가동 또는 재가동 명령    ─┘
```

그리고 같은 사건을 한 번 더 쓴다 — 설비별로 묶어서.

```
벨트 정지  →  작업자 접근  →  이물 제거  →  재가동      = 정지 에피소드 1건
                                                            ↓
                          한 달치를 설비별로 세면        "이 컨베이어에서 43번 반복됐고
                                                          그중 32번 사람이 회전체 옆에 들어갔다"
```

"사람이 있습니다" 가 아니라 **"정상 생산이 아니라 설비 이상에 대응하려고 위험구역에
들어가는 행동이 이 설비에서 반복된다"** 를 말한다.

- 차단은 기계가 하고, 위험 사건 조치와 개인 시건 해제는 사람이 기록한다
- 위험 사건이 종결되고 시건이 모두 풀린 뒤 운전 담당자가 다시 요청하면 인터록을 재판정한다
- 개인 시건(LOTO)이 하나라도 남아 있으면 재가동할 수 없다
- AI 서비스가 죽어도 인터록 판정은 DB 만 보고 동작한다 (fail-safe)

기존 LOTO 와 방호장치를 대체하지 않는다. 안전절차 누락과 작업자 간 의사소통 오류를 보완하는
**AI 이중 안전장치**다.

| — | `/manager/metrics` | 도입 효과 6개 지표 |

## 입력은 CCTV 가 찍어 둔 장면이다

안전관리자는 자기 컴퓨터에서 사진을 올리는 사람이 아니다. **카메라가 이미 찍어 둔 장면
중에서 볼 것을 고르는** 사람이다. 그래서 이 앱의 분석 화면에는 파일 선택 대화상자가 없다.

```
CCTV — 위험구역 접근 감지 → 스냅샷 자동 저장 (POST /api/snapshots)
                                    ↓
                    스냅샷 수신함 — 카메라 · 촬영 시각 · 촬영 이유
                                    ↓
                  안전관리자가 볼 장면을 골라서 → AI 분석 → 위험 사건
```

수신할 때 프레임 한 장을 바로 판정해 **사람 박스를 붙여 둔다.** 카메라가 "위험구역에
접근했다" 고 말하면 그 근거가 함께 있어야 하고, 수신함 썸네일에서 접근한 작업자에게 진한
박스가 뜨는 게 그 값이다. 구역 밖 사람은 얇고 흐리게 — **박스는 빨개지지 않는다.** 기계는
사람이 어디 있는지 탐지할 뿐 위반을 정하지 않고, 빨강은 사람이 확정한 뒤에만 쓴다.

1차 탐지는 판정이 아니다. 잔류도 설비 상태 결합도 사건 생성도 하지 않는다 — 그건 여러 장을
묶는 시퀀스 분석 몫이다. 그리고 탐지가 실패해도 수신은 성공한다: AI 가 재시작 중이라고
카메라가 보낸 장면을 잃으면 정작 필요한 순간의 근거가 사라진다. 실패한 장면은 화면에
"탐지 안 됨" 으로 남는다 — **"탐지하지 않았다" 와 "탐지했는데 사람이 없었다" 는 다른 사실이다.**

이 구조의 또 다른 실익은 **시각이 이미 붙어 있다**는 점이다. 분석할 때 사람이 촬영 시각을
입력하면 오타 하나가 잔류시간을 거짓으로 만든다. 찍힌 순간에 한 번 기록되면 그 뒤로는
데이터고, 분석 화면에서 사람이 넣는 값은 하나도 없다(설비 상태만 데모에서 받고, 실운영은
PLC 가 준다).

```
정상 운전        벨트 정지        작업자 접근       위험구역 진입      재가동 요청
  14:32:07   →    14:32:37   →    14:33:07    →    14:33:37     →    14:34:07
   (1장)          (2장)           (3장)            (4장)             (5장)
                                                                      ↓
                          한 시퀀스로 보면 CAUTION → WARNING → CRITICAL 한 건의 서사
```

한 장으로는 "사람이 있다" 까지다. 여러 장이라야 **"설비 이상에 대응하려고 위험구역으로
접근하는 행동"** 이 된다. 그래서 장면을 한 장씩 판정하지 않고 시퀀스로 묶는다.

영상 경로와 세 가지가 다르고, 셋 다 정직해야 성립한다.

| | 영상 | 캡처 이미지 |
|---|---|---|
| 샘플링 | 6fps | 업로드한 장수 그대로 |
| 작업자 추적 | ByteTrack | **안 한다** — 프레임이 초 단위로 떨어지면 모션 예측이 성립하지 않는다 |
| 진입 판정 | 2프레임 투표(0.33초) | **한 장이 곧 관측** — 6fps 기준 히스테리시스를 30초 간격에 걸면 "진입 확정까지 60초" 가 된다 |
| 잔류시간 | 초 단위 | **프레임 간격 단위** — 30초 간격이면 "6.4초 잔류" 는 만들 수 없다 |

마지막 줄은 분석 결과의 `warnings` 로 화면까지 그대로 나간다. 지우면 안 되는 문장이다.

그리고 **관측되지 않은 공백은 존재의 증거가 아니다.** 고른 두 장 사이가 너무 벌어지면
(전형 간격의 3배, 최대 180초) 그 앞뒤를 이어 붙이지 않고 사건을 끊는다. 이어 붙이면
6.7시간 떨어진 두 장에서 "잔류 24,261초" 가 나오는데, 그건 우리가 본 것이 아니다.

이미지에 박힌 타임스탬프를 OCR 하지 않는다 — 번인 문자열은 카메라마다 위치·서체가
다르고, 한 글자를 잘못 읽으면 잔류시간이 조용히 거짓이 된다. 시각은 찍은 장치가 준다.

## AI가 하는 일 · 하지 않는 일

**한다** — 작업자 탐지, 위치 추적, 위험구역 진입·잔류 판단, 설비 상태 결합, 위험 순간 자동
캡처, 설비별 반복 패턴 집계.

**하지 않는다** — 얼굴 인식, 개인 식별, 보호구 착용 판정, 작업자 감시.

**할 수 없는 것을 한다고 말하지 않는다** — 두 가지를 특히 조심했다.

| | AI 가 하는 일 | 사람이 하는 일 |
|---|---|---|
| 제품 걸림 | 걸림 자체는 못 본다. 관측하는 건 `벨트 정지` × `위험구역 접근` 두 개다 | 원인을 걸림 / 계획 정비로 확정 (실운영은 PLC 가 준다) |
| 안전대 | 구역 **진입** + 하네스 **착용** 추정 | 훅을 실제로 걸었는지 **체결** 확인 |

안전대의 경계선은 실제로 픽셀을 재서 그었다. 데모 화각(`samples/` 의 CAM 05)에서:

```
척도            안전모 폭 28cm ≈ 47px   →  1.7 px/cm
하네스 웨빙     45mm  ≈  7~8px         →  보인다  (어깨 스트랩·허리 버클·D링 육안 확인)
카라비너        10~24cm ≈ 17~41px      →  크기는 되지만 몸·구조물에 가린다
```

그래서 **착용까지는 본다.** 전체 프레임에서 7px 스트랩을 찾는 게 아니라
`사람 탐지(conf 0.9) → 상체 crop(190×170px) → 착용/미착용 분류` 로 쪼개면, 스트랩이
입력 폭의 4% 가 되어 볼 수 있는 크기가 된다.

그리고 **버튼을 갈라 두었다.** 수신함에서 장면을 고르면 두 버튼이 뜬다.

| 버튼 | 질문 | 공급자 | 결과 |
|---|---|---|---|
| 위험구역 분석 | 진입·잔류했나 | **우리 로직** (사람 탐지 + 폴리곤 + 설비 상태) | 위험 사건 · 정지 에피소드 |
| 안전대 착용 판정 | 하네스를 입었나 | **Roboflow 호스팅 추론** (남의 학습 결과) | 장면별 착용 판정 |

한 버튼에 묶지 않은 이유는 공급자가 다르기 때문이다. 남의 추론 서비스가 죽는 날 우리
판정까지 같이 의심받으면 안 된다. `GET /health` 의 `harness.provider` 가 어디서 판정하는지
밝히고, 실패하면 그 이유(`harness.error`)가 화면까지 그대로 올라간다.

**체결은 보지 않는다.** 두 가지 이유다. ① 훅이 안 보이는 게 "미체결" 인지 "가려짐" 인지
구분할 방법이 없다 — 미탐과 무탐이 같은 그림이다. ② 체결의 옳고 그름은 물체가 아니라
**관계** 다. 정격 앵커인가, 난간인가(난간은 앵커로 부적합), 자기 하네스 D링인가(가짜 체결).
픽셀에 그 정보가 없다. 산업계도 이건 홀센서·스트레인게이지로 푼다.

이 선언은 문서가 아니라 계약이다 — `GET /health` 의 `harness.judgesAttachment: false`.
`DangerZone.requiresHarness` 로 표시한 구역의 사건에는 AI 추정 한 줄과 사람이 누르는
체결 확인 버튼이 나란히 뜬다.

COCO `person` 클래스 하나만 본다. `track id` 는 한 영상 안에서만 쓰이는 익명 번호이고 분석이
끝나면 사라진다. 저장되는 캡처는 머리 부분을 흐리게 처리한다. 이 선언은 문서가 아니라
`GET /health` 의 `identifiesIndividuals: false`, `faceBlur: true` 로 응답에 박혀 있다.

## 증명 지표

사고 건수로 효과를 주장하지 않는다. 실제로 잰 시간과 횟수로만 말한다.

| 지표 | 계산 |
|---|---|
| 위험 감지 소요시간 | 구역 진입 → AI 위험 판정 |
| 관리자 조치 소요시간 | 통보 → 인지 / 판단 / 현장 조치 완료 |
| 위험구역 노출시간 | 구역별 · 24시간대 히트맵 |
| 차단한 위험 재가동 | 차단 요청 수, 그중 사람이 확정한 수 |
| CCTV 확인 업무시간 | 전체 영상 길이 대비 실제로 본 구간 |
| 오탐 / 미탐율 | 미판단(보류·대기)은 분모에서 제외 |

그리고 사업주에게는 안전 지표가 아니라 이 네 개를 보여준다.

| 지표 | 계산 |
|---|---|
| 걸림 대응 정지 횟수 | 설비별 `cause = JAM` 에피소드 수. 계획 정비는 뺀다 |
| 위험구역 접근 동반 | 그중 정지 구간 안에 위험 사건이 있었던 건수 |
| 평균 복구시간 | 정지 → 재가동. 재가동 전인 건은 평균에서 제외 |
| 누적 생산중단시간 | 걸림 정지 구간의 합. **계획 정비는 손실이 아니라 계획이라 뺀다** |

금액은 `누적 중단시간 × 설비별 분당 손실단가` 로만 만든다. 단가는 **관리자가 설비마다 직접
입력하는 값**이고, 비워 두면 금액 칸이 아예 사라진다. 라인마다 시간당 생산량이 다른데
우리가 추정한 원화 숫자 하나를 얹으면 나머지 지표의 신뢰까지 같이 깎인다.

## 실행

```bash
# 1) AI 서비스
python3 -m venv ai/.venv
ai/.venv/bin/pip install -r ai/requirements.txt

# 2) 웹
cd web && npm install
cp .env.example .env          # DATABASE_URL, JWT_SECRET 채우기
npx prisma migrate deploy && npx prisma db seed
cd ..

# 3) 함께 띄우기
./start-dev.sh                # AI :8000 + 웹 :3000
```

## 데모 영상 촬영

핵심: **설비가 실제로 재가동하는 영상은 필요 없다.** 설비 상태 타임라인이 요청 파라미터라
"사람이 구역 안에 머무는 영상"만 있으면 되고, 재가동 순간은 JSON 으로 주입한다. 실운영에서는
PLC / LOTO 가 그 값을 준다 — 눈속임이 아니라 정확히 그 시스템의 실제 구조다.

삼각대 위 휴대폰(내려다보는 각도, 고정), 바닥에 마스킹테이프 사각형, 사람 2명. 각 15~25초:

| 테이크 | 내용 | 기대 결과 |
|---|---|---|
| A | 구역에 들어가 12초 작업 → 동료가 스위치 ON | WARNING → **CRITICAL** 로 에스컬레이션 |
| B | 같은 작업, 설비는 계속 정지 | WARNING 까지만. **CRITICAL 없음** |
| C | 경계를 스치며 지나감 | **아무 이벤트도 안 남** |

테이크 C 가 심사에서 가장 강하다. 대부분 "탐지됩니다"만 보여주고, "탐지 안 됩니다"를
의도적으로 보여주는 팀은 드물다.

`samples/` 에 클립을 넣고 `samples/zones/take-a.json`(예시는 `*.example.json`)에 구역·설비
타임라인·정답 구간을 적으면 채점된다:

```bash
ai/.venv/bin/python -m ai.eval.score_demo
```

### 알아 둘 것

- **CCTV 영상은 브라우저 → Vercel Blob 으로 직접 올라간다.** Vercel Function 요청 본문이
  4.5MB 하드 리밋이라 서버 액션으로 중계할 수 없다.
- **영상 분석은 잡+폴링이다.** HF Space 게이트웨이(~60초)와 업로드 시간을 우회하고, 덤으로
  진행률 바가 생긴다.
- **AI 캡처는 휘발성이다.** HF Space 는 재시작하면 디스크가 날아간다. 안전관리자가 위험으로
  확정한 건만 Blob 으로 옮겨 영구 보관한다 — AI 의 의심은 휘발, 사람의 판단은 영구.
- 데모는 업로드 영상 기반이다. 상용 배포에서는 RTSP 게이트웨이를 붙인다.
- `ultralytics` 와 COCO 가중치는 **AGPL-3.0**.
